# Plan D.4 — GraphQL backend cross-stack consumption

**Status:** Approved 2026-06-02
**Parent spec:** `docs/superpowers/specs/2026-06-02-plan-d3-multi-backend-cross-stack-design.md`
**Predecessors:** Plan D.2 (single-backend REST), Plan D.3 (multi-backend REST)
**Successor (planned):** none — closes the cross-stack codegen story for v1

---

## Goal

Plan D.3 generates a typed TypeScript API client per `backend-rest-api` upstream when
a `frontend-app` node consumes one. GraphQL upstreams (`backend-graphql`) were
explicitly deferred ("needs `@graphql-codegen/typescript` instead — own future plan").

Plan D.4 closes that gap. When a `frontend-app` node consumes a `backend-graphql`
upstream, the engine generates a typed GraphQL client via
`@graphql-codegen/typescript` (+ `@graphql-codegen/typescript-operations`) and
threads it into `priorArtifact.generatedFiles` alongside any REST clients from D.3.

## Architecture decisions (locked)

1. **Coexistence with REST cross-stack** — A frontend can consume any mix of
   `backend-rest-api` and `backend-graphql` upstreams. The cross-stack block in
   `makeLaunchRitual` walks `node.consumes` once and dispatches to the right
   generator per upstream kind. Resulting `generatedFiles` is the concatenation
   of REST + GraphQL outputs.
2. **Naming convention** — GraphQL clients are always named per-backend:
   `lib/graphql-client-{backendNodeId}.ts`. We do NOT preserve a canonical single-
   backend name like D.2 did for REST, because no template currently imports a
   `@/lib/graphql-client` path — every consumer is generated by the LLM with
   knowledge of the node id.
3. **Pure helper** — `generateGraphqlClient(graphqlSchema, opts)` is a pure
   function (no I/O) returning `{ path, contents }`. Tests inject a stub SDL.
4. **Operations are optional** — `generateGraphqlClient` accepts an optional
   `operations` string (raw GraphQL document text). When present, the
   `@graphql-codegen/typescript-operations` plugin is also run and its output is
   concatenated into the same file. When absent, only the schema-derived
   `typescript` plugin output is emitted.
5. **Artifact contract** — A new `BackendGraphqlArtifact` Zod schema joins the
   registry under kind `"backend-graphql"`. Shape:
   `{ schemaVersion, kind: "backend-graphql", graphqlSchema, operations?, sandboxId, previewUrl?, envContract }`.
   No `routes` field — GraphQL has a single endpoint by convention; the schema
   itself is the surface.
6. **No deduplication** — Each GraphQL backend gets its own file, same as REST
   under D.3.
7. **Order-stable** — Generated files preserve `node.consumes` order so a given
   DAG produces a deterministic `generatedFiles` array across runs.

## Generated file path table

| Upstream kind        | Count | File path(s)                                            |
|----------------------|-------|---------------------------------------------------------|
| `backend-rest-api`   | 0     | omitted                                                 |
| `backend-rest-api`   | 1     | `lib/api-client.ts` (D.2, preserved)                    |
| `backend-rest-api`   | 2+    | `lib/api-client-{backendNodeId}.ts` per backend (D.3)   |
| `backend-graphql`    | 0     | omitted                                                 |
| `backend-graphql`    | 1+    | `lib/graphql-client-{backendNodeId}.ts` per backend     |
| MIXED REST + GraphQL | any   | concatenation of both lists, in `node.consumes` order   |

## Out of scope (later)

- A bundled GraphQL request runtime (e.g. `graphql-request` wrapper file)
- Cross-backend GraphQL schema stitching / federation
- Persisted queries
- A barrel `lib/graphql-clients/index.ts` re-export
- Verifying the LLM actually USES the generated clients
- Subscriptions / `@graphql-codegen/typescript-react-apollo`-style framework
  hooks (we emit framework-agnostic types only)

## Backward compatibility

- A workflow with only `backend-rest-api` upstreams produces EXACTLY the same
  `generatedFiles` array as before this plan (existing D.2/D.3 tests stay
  green).
- A workflow with zero relevant upstreams still omits `generatedFiles`.
- The cross-stack scan is purely additive — no REST upstream is reclassified.

## Shippable result

A workflow with 1 frontend node + 1 REST backend + 1 GraphQL backend (frontend
`consumes` both) launches the frontend ritual with
`priorArtifact.generatedFiles` containing TWO files: `lib/api-client.ts` (for
the single REST backend) and `lib/graphql-client-{graphqlNodeId}.ts` (for the
GraphQL backend). Each file's contents pass a sanity regex (`export\s+type` /
`export\s+interface`). Existing single-REST-backend workflows still emit only
`lib/api-client.ts`.
