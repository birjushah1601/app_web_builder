# Plan D.2 — Frontend cross-stack consumption of BackendArtifact

**Status:** Approved 2026-05-31
**Parent spec:** `docs/superpowers/specs/2026-05-26-multi-artifact-workflow-design.md` (§10 frontend-app entry)
**Predecessors:** Plans A (engine), B (planner), C (graph UI), D (backend producer + typed handoff), E (tests), F (iac + deploy)
**Successor (planned):** Plan D.3 — multi-backend cross-stack; GraphQL client generation

---

## Goal

When a `frontend-app` workflow node `consumes` a `backend-rest-api` upstream node, the WorkflowEngine generates a typed TypeScript API client from `BackendArtifact.openApiSpec` (via the `openapi-typescript` npm library) and threads it into the frontend ritual's `priorArtifact.generatedFiles`. The developer role's prompt-assembler surfaces the generated file to the LLM as "pre-generated files now in your sandbox", so the LLM can emit code that imports from it.

This closes the typed-handoff loop on Plan D's central thesis: backend produces typed artifact → frontend gets a typed client without any LLM prompt-engineering for the schema translation.

## Architecture decisions (locked)

1. **Mechanical codegen, not LLM** — Use the standard `openapi-typescript` library. Deterministic, fast, no LLM cost. LLM only writes the code that USES the client; the client itself is generated mechanically.
2. **Generation happens in-process** at the workflow-engine layer (atlas-web's process) when `makeLaunchRitual` builds priorArtifact. Not in the sandbox. Saves a round-trip + tightens the boundary: workflow engine knows about cross-stack handoffs, roles don't.
3. **Single-backend per frontend for v1.** If a frontend node declares `consumes` with 2+ `backend-rest-api` artifacts, the engine throws a clear error: `"Plan D.2 v1: multiple backend upstreams not supported (frontend node 'X' consumes 'A', 'B'). Multi-backend cross-stack is Plan D.3."`
4. **Delivery via `priorArtifact.generatedFiles`** — a new top-level array on the priorArtifact object: `Array<{ path: string; contents: string }>`. Opaque to the conductor (RoleInvocation.priorArtifact is `unknown`). Developer role's prompt-assembler reads it.
5. **File path = `lib/api-client.ts`** — fixed convention. Matches Next.js `@/lib` alias used by the atlas-next-ts template. Plan D.3 multi-backend can extend to `lib/api-client-{backendNodeId}.ts`.
6. **Developer role writes the file** as part of its diff — we tell the LLM "the api-client has been pre-generated; here are its contents; include `lib/api-client.ts` in your diff exactly as shown so it ends up in the sandbox." The existing sandbox-apply machinery handles the write. This avoids introducing a new pre-developer file-injection step.
7. **No runtime verification** — we DON'T check that the LLM's emitted code actually imports from `lib/api-client.ts`. Prompt-engineering quality is a follow-up. Plan D.2 ships the mechanism; the LLM's adoption rate is a separate concern.

## Generated client shape

`openapi-typescript` emits a single file with these exports (default config):

```ts
// lib/api-client.ts (generated by openapi-typescript)
export interface paths { /* per-route request/response types */ }
export interface components { /* schemas */ }
export type webhooks = Record<string, never>;
export type $defs = Record<string, never>;
```

For Plan D.2 v1, we emit the raw openapi-typescript output as-is. We don't wrap it with a fetcher helper (that's another polish task — Plan D.3 could add a thin `createClient()` wrapper from `openapi-fetch`).

## Out of scope (Plan D.3 / later)

- Multiple backend upstreams per frontend node
- GraphQL client generation (`backend-graphql` upstream — needs `@graphql-codegen/typescript` instead)
- A bundled `createClient()` wrapper (openapi-fetch) so the LLM can write `client.GET("/users", ...)` instead of raw fetch
- Typed exceptions / error-class generation
- Hot-reload when the backend artifact changes (re-emit api-client and re-run developer)
- Verifying the LLM actually USES the generated client (a structural eval rubric check)
- Image-server / asset-server clients (the same mechanism could later cover other typed artifact kinds)

## Shippable result

A workflow with a backend node + a frontend node that `consumes` the backend will:
1. Backend node runs first → emits `BackendArtifact` with openApiSpec → workflow engine persists.
2. Scheduler launches the frontend node. `makeLaunchRitual` builds priorArtifact, sees the backend-rest-api upstream, runs `openapi-typescript` on its openApiSpec, attaches `{ path: "lib/api-client.ts", contents: "..." }` to `priorArtifact.generatedFiles`.
3. Frontend ritual dispatches developer role with the augmented priorArtifact.
4. Developer's prompt now includes a "Pre-generated files (already in your sandbox via the diff you'll emit)" section that surfaces the file path + contents.
5. Developer's emitted diff includes `lib/api-client.ts` verbatim.
6. Sandbox apply writes it; subsequent frontend builds can `import type { paths, components } from "@/lib/api-client"`.

The typed handoff is now end-to-end mechanical — no LLM prompt-engineering required to translate the backend's schema into the frontend's types.
